## 1. 官方 hook：成立

**事件名**（来自 code.claude.com/docs/en/hooks）：回合结束 `Stop`；权限请求 `PermissionRequest`；通知 `Notification`，按 `notification_type` 区分，含 `permission_prompt`、`idle_prompt`、`elicitation_dialog`、`agent_needs_input` 等；另有 `SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionDenied`、`StopFailure`。

**实测证据**：

- 所有挂上的事件在 Desktop 会话里都触发了：`SessionStart`、`UserPromptSubmit`、`PreToolUse`、`PermissionRequest`、`Notification`、`Stop`。
- 修改 `settings.local.json` 后，已在运行的会话立即生效，不需要重开会话。
- 每个事件都带 `session_id`（36 位 UUID）和 `transcript_path`。`transcript_path` 的文件名就是 `<session_id>.jsonl`。
- 会话的第一个 `SessionStart` 和 `UserPromptSubmit` 触发时，记录文件还不存在；从第一个 `PreToolUse` 开始存在。
- `PermissionRequest` 带 `tool_name` 和 `tool_input`。Bash 的 `tool_input.command` 是命令全文（测试命令 22 字，字段长度 22），另有 `description` 和 `permission_suggestions`。
- `Stop` 带 `last_assistant_message`，是最后一条回答的全文（各轮长度从 8 到 2179 字不等，与记录文件里的回答一致）。
- `Notification(permission_prompt)` 在权限请求后约 6 秒触发，与文档描述的 Desktop 行为一致。但第 9 轮的权限请求一直没收到这个通知（当时窗口最小化，审批拖了约 30 秒），**不可靠**。
- 整个过程中没有出现 `idle_prompt`。
- **bypass 模式下**，普通工具不触发 `PermissionRequest`，但 `AskUserQuestion` 会触发：`tool_name = "AskUserQuestion"`，`tool_input.questions` 是问题列表。6 秒后还会跟一个 `Notification(permission_prompt)`。用户的会话跑在 bypass 模式，所以这是"Claude 明确提问"的事件来源。
- **在 Desktop 里点「拒绝」后回合直接结束，不触发 `Stop`**。记录文件末尾是一条被拒绝的 tool_result 和一条空的用户消息。文档说 `Stop` 在用户中断时不触发，与此一致。

**对 DESIGN.md 的影响**：

- 3.4 节"事件来源"成立。立刻级事件用 `PermissionRequest` 一个事件就够了：普通工具的审批和 `AskUserQuestion` 提问都走它，用 `tool_name` 区分。不要依赖 `Notification(permission_prompt)`。
- 3.3 节完成通知需要的回答全文和选项段，`Stop.last_assistant_message` 已经直接给出。会话记录文件从"辅"降为"基本用不上"，可以留作 `Stop` 缺失时的兜底。
- 会话识别用 `session_id`。`SessionStart` 里有可选的 `session_title`，这次实测未出现，标题仍要从别处取（例如无障碍树里的会话列表）。
- 拒绝后没有 `Stop`。侧通道写入「拒绝」后要自己把这次审批标为已结束，不能等回合结束事件。
- 首版不需要 `idle_prompt`；它在 Desktop 里没观察到。

## 2. 填字并点发送：有条件成立

**已知控件**全部确认：输入框 `ControlType.Edit`、Name=`Prompt`，支持 ValuePattern 和 TextPattern；发送按钮 Name=`Send`，回合进行中变为 `Stop`。主进程按 `Path like '*\WindowsApps\*'` 找 `claude` 进程，取它的顶层窗口即可。第一次查询时 Chromium 的无障碍树可能是空的（只有标题栏三个按钮），几秒后再查就完整了。

**窗口正常时**：`ValuePattern.SetValue` 写入后，立即读回只有 1 个字，约 1 秒后读回完整、`Send` 变为可用。等 `Send` 可用再 Invoke，8 次里 8 次成功发送（每次都收到 `UserPromptSubmit`；除被拒绝的那轮外都收到 `Stop`）。另有 1 次失败：切权限模式后弹出了「Try auto mode」提示框，当时 Invoke `Send` 无效；关掉提示框后重试成功。

**窗口最小化时**：

- `SetValue` 不生效：最小化期间读回一直是 1 个字，`Send` 不可用。恢复窗口后 1 秒内内容到位。
- Invoke `Send` 或审批按钮不报错，但什么也不发生；**恢复窗口后被排队的点击才执行**。
- 用 WindowPattern 把窗口从最小化恢复到 Normal 可以正常工作，之后再最小化也正常。

**可行的写入序列**（已端到端跑通一次）：恢复窗口 → 切到目标会话 → `SetValue` → 轮询直到 `Send` 可用且读回长度等于预期 → Invoke `Send` → 以 `UserPromptSubmit` hook 或按钮变成 `Stop` 作为送达确认 → 切回原会话 → 恢复原窗口状态。

**对 DESIGN.md 的影响**：3.5 节"若需恢复窗口，操作完恢复原状"从"若需"改为**必须**：写入前一律恢复窗口，写完再最小化。不能直接 Invoke 而不等待：要等 `Send` 可用并读回校验。写入前要检查有没有遮挡用的提示框（例如 `Window` 名为「Try auto mode」，可点里面的 `Dismiss` 关掉）。

## 3. 权限对话框：成立

结构（在主面板 `Group[Primary pane]` 内）：

```
Group  class="epitaxy-approval-card …"   ← 审批卡片
  Text  "Allow Claude to " / "run" / " " / <description> / "?"
  Text  "This command requires approval"
  Text  <命令全文>
  Button "Deny 1"           Invoke
  Button "Always allow 2"   Invoke
  Button "Allow once 3"     Invoke
```

主面板里同时出现一个 `Button "Needs your input"`。

- 三个按钮名字固定、带快捷键数字，按精确名字 `Allow once 3` / `Deny 1` 能唯一定位；都支持 InvokePattern。
- 「Allow once 3」：Invoke 后工具执行、回合继续、最后触发 `Stop`。
- 「Deny 1」：Invoke 后卡片消失、回合结束，不触发 `Stop`（见第 1 项）。
- 最小化时的行为与第 2 项相同：点击被排队，恢复窗口后才执行。
- 卡片内的命令全文和 `PermissionRequest.tool_input.command` 一致，侧通道用 hook 里的就够了，不需要读树。

**对 DESIGN.md 的影响**：3.5 节审批写入可行，前提同第 2 项（先恢复窗口）。定位按钮应限定在当前会话的审批卡片内，以防多个会话同时有卡片；本次只测了一个会话有卡片的情况。按钮名里带的数字 `1`/`3` 可能随版本变化，实现时用前缀匹配 `Allow once` / `Deny` 更稳。

## 4. 选项格式契约：成立

**测试方法**：第 1–2 轮把指令直接写在 prompt 开头。第 3–9 轮改用 `UserPromptSubmit` hook 的 `additionalContext` 注入（这是实现时真正会用的方式），并只对测试会话生效。注入的那一行：

> [用户不在电脑前] 回答结束时，若有合理的下一步，最后一段以单独一行「选项：」开头，下面最多 3 个编号项，每项一句话、不超过 40 字，第 1 项固定为「按刚才说的继续」；没有合理下一步就省略这一段。

用脚本逐项检查最后一条回答：标题是否完全一致、项数、编号、每项字数、第 1 项文字。

| 轮 | 任务类型 | 结果 |
|---|---|---|
| 1 | 运行一条命令并报告输出 | 无选项段（合理） |
| 2 | 列出 docs 下的文件 | 无选项段（可算合理） |
| 3 | 建议先实现哪个模块 | 合规，3 项，第 1 项正确，最长 26 字 |
| 4 | 找 DESIGN.md 的遗漏 | 合规，3 项，最长 20 字 |
| 5 | 一句话解释概念 | 无选项段（合理） |
| 6 | 起草目录结构 | 合规，3 项，最长 25 字 |
| 7 | 对比术语表和设计 | 合规，3 项，最长 23 字 |
| 8 | 触发权限后点「拒绝」 | 回合被拒绝中断，无回答，不计入 |
| 9 | 怎么拆任务 | 合规，2 项，最长 21 字 |

有明显下一步的 5 轮（3、4、6、7、9）全部合规：标题都是单独一行的「选项：」，都在回答最后，第 1 项都是「按刚才说的继续」，没有超过 40 字的项。没有下一步的 3 轮（1、2、5）都省略了选项段，没有硬凑。

注入不影响正文：回答其余部分与平时一样。

**对 DESIGN.md 的影响**：

- 3.2 节可以照原样实现，注入方式定为 `UserPromptSubmit` hook 返回 `additionalContext`。它不进 prompt 文字，Desktop 界面上看不到；只在离开状态返回。
- 固定标题用「选项：」，侧通道解析时匹配最后一个单独成行的「选项：」。
- 有效样本只有 8 轮、一个模型（Opus 5.5）。上线后侧通道应在解析失败时退回"只发前 600 字、不带按钮"，不要假设一定合规。
- 第 2 轮这类"列完了"的回答，模型判断为没有下一步。用户可能希望这时也有「按刚才说的继续」以外的选项；这属于措辞调优，不影响可行性。

### 测试中发现并已修复的问题

- **界面写入在有无名按钮时崩溃**（PR #9）。
  - 现象：目标会话有草稿时，本该返回 `draft_present`，实际返回 `error_RuntimeException`，并误发一条 ⚠️ 故障提醒。消息靠"坏了就改走辅助会话"才送达。
  - 原因：Desktop 里出现了 Name 为 null 的按钮，`$n.EndsWith(...)` 抛异常。
  - 修复：三处读按钮名的地方都先转成字符串。修复后同一场景返回 `draft_present`，不发送任何内容。
- **切换会话等待太短**（PR #9）。打开一个对话很长的会话实测要约 12 秒，原来只等 5 秒，可能误报 `switch_failed`。改为最多等 15 秒。
- **守护进程重启后回复旧通知找不到会话**（PR #10）。
  - 原因：消息和会话的对应关系只在内存里，重启就丢。
  - 修复：每条通知第一行末尾带 `#` 加会话 id 前 8 位。回复时如果内存里查不到，就从被回复消息的文字里取这个标记去找会话。找不到就拒绝，不会转给别的会话。
  - 重启前的按钮仍然失效，现在会提示改用回复。
- **通知标签用了内部名**（PR #3）。`SessionStart` 的 `session_title` 是 Claude Code 内部的短名（如 `ccmonitor-write-module-test-bd43f8`），现在改为优先用 Desktop 侧边栏标题。

## 托盘「停用」崩溃修复后补测（2026-10-13 19:26 – 19:33，PR #74，#72）
