## 1. 要解决的问题

用户不在电脑前时，电脑上的 Claude Code Desktop 本地会话需要用户**介入**（审批、回答提问、给下一步指令）。官方 Remote Control 已经能在手机上看会话、发消息、审批，但**一次介入的成本太高**：要在手机上打字，而在电脑上通常是点一下建议就走。

**成功指标**：在手机上完成一次介入所花的时间（介入成本）。

## 3. 决定

### 3.1 范围与边界

- 只针对本地会话；本地是硬约束（需要本机文件和本机工具）。
- 所有会话默认连接 Remote Control，不另设"标记"概念。
- 电脑前提：常开、不锁屏、Desktop 可最小化、手机走移动网络。
- 立刻级事件：权限审批、Claude 明确提问。延后级：任务完成、出错或卡住。"下一步可以做 X"不单独通知。
- 可接受延迟：一分钟内。使用模式以"偶尔看一眼"为主。
- 首版不做卡住/出错检测（v2 已完成，见第 5 节）。
- 原定的"一周官方推送基线"取消：Telegram 无论如何承担全部通知，官方推送无论如何保留，基线不再影响任何决定。

### 3.2 用"选项"替代"建议"

- 官方建议在本地会话里无法从记录文件、hook 或无障碍树取得。（2026-10-11 追加：可以用"按 Tab 接受再读输入框"的办法取得原文，见 3.8；选项仍保留，两者并存。）
- 改由**会话本身的模型**在回答结尾给出编号**选项**。它随 Remote Control 原样同步到任何设备，不依赖 Desktop 的任何内部结构。
- **只在离开状态出现**（2026-10-12 用户改定，取代 2026-10-11 19:08 的"总是出现"）：在电脑前不发通知（3.3），选项段只会挤掉 Desktop 自己的输入框建议，所以在电脑前不注入。离开时注入的一行带「[用户不在电脑前]」前缀。读不到离开状态时通知照发，这时注入不带前缀的同一行，以免模型误以为用户不在。代价：在电脑前开始、中途离开的那一轮，完成通知没有选项按钮，只有 💡 官方建议。
- 注入方式：`UserPromptSubmit` hook 在离开状态返回 `additionalContext`，不改 prompt 文字，Desktop 界面上看不到。
- 格式契约：回答最后一段以单独一行的固定标题「选项：」开头；最多 3 个编号项；每项一句话、不超过 40 字；每项是一条可以直接发出的具体指令；不列需要用户先提供材料或信息才能执行的项（2026-10-12 用户要求：格式实测中 33 项里有 2 项要用户先贴材料，在手机上没法一键发出）；没有合理下一步时不出现这一段。
  - 2026-10-12 去掉"第 1 项固定为「按刚才说的继续」"（VERIFY.md 第 4 项验证的原文里有）：模型照写这一项后，Desktop 的官方建议几乎总是照抄它，💡 按钮和 1 号选项重复。去掉后已实测（2026-10-12，VERIFY.md「去掉固定第 1 项后的选项格式」）：有下一步的 11 轮全部合规，没有下一步的 5 轮里 4 轮省略、1 轮多给了 2 个追问（格式仍合规）；英文回答也用「选项：」标题。官方建议和选项是否仍重复，无界面运行只拿到 1 条建议，它和一个选项完全相同，样本不够下结论。
- 解析：取最后一个单独成行的「选项：」之后的编号项。解析失败时完成通知退回只发正文、不带选项按钮，不假设模型一定合规。
- 标题也认「选项:」（半角冒号）和英文 `Options:`（不分大小写）：用英文回答的会话会把标题译成 `Options:`（2026-10-11 19:18 实测，因此没出按钮）。
- 2026-10-12 用户要求：用英文回答时标题明确写 `Options:`。注入的那一行写成「…以单独一行「选项：」开头（用英文回答时写「Options:」）…」。此前的实测里英文回答一直沿用「选项：」，能解析但和正文语言不一致。
- 每项"不超过 40 字"按中文字算：中文等全角字算 1，英文字母、数字、标点算半个。英文选项常超过 40 个字符，按字符数会被整段拒绝。
- 解析不检查各项的内容，只检查标题、编号、项数和长度。

### 3.3 侧通道（Telegram）

- 承担全部六项：立刻级通知、延后级通知、显示选项、一键选选项、自由 prompt、审批。
- **只在离开状态发通知**（2026-10-12 用户改定，原为不管在不在电脑前都发）：在电脑前时各类会话通知都不发到 Telegram；读不到离开状态时照发，宁多勿漏。守护进程自己的提示（启动、故障提醒、排队结果）不受影响。
- Bot 输入框下有一个 /away 按钮（回复键盘，点了就发出该命令），**只在不处于离开状态时显示**，不设 /back 按钮（2026-10-12 用户改定）；「/」菜单里列出全部命令。Telegram 只能随消息换键盘，所以每条回答都带当前状态对应的键盘；离开状态变化时（键鼠空闲满 3 分钟、回到电脑前、手机上点按钮），守护进程 15 秒内发一条静音消息「已离开电脑，通知转到这里」或「已回到电脑前，不再转发通知」来显示或收起按钮。话题模式下 Telegram 按话题分别记住键盘（2026-10-12 实测：消息发在主对话时，会话话题里的按钮没有变），所以这条消息发到用户最近一次操作所在的话题；那个话题已被删时改发主对话。
- 官方手机推送和 Claude app 的审批**同时保留**。原因：用户要把通知收在一个地方，但不放弃官方路径。
- 完成通知带最后一条回答的**全文**（2026-10-11 用户改定，原为前 600 字）。超过 Telegram 单条上限时按段落拆成多条，标「续 2/3」，不在代码块中间断开；按钮放在最后一条；回复其中任何一条都能找到会话。
- **失效的按钮会被收掉**（2026-10-13 用户要求）：在电脑或别的设备上操作后，Telegram 上的旧按钮不再留着。按会话记下哪些通知还带按钮，收到该会话之后的 hook 事件时把已失效的按钮去掉（`editMessageReplyMarkup` 清空）：新的 `UserPromptSubmit` 收掉完成通知的选项和 💡；新的 `PermissionRequest` 收掉之前的审批和提问；`Stop`、`StopFailure`、`SessionEnd` 收掉全部。事件先于它自己产生的通知处理，新通知的按钮不受影响。点到已失效的按钮（用过、或重启后）时，除了提示，也把那条消息的按钮收掉。会话已往下走时，迟到的官方建议不再补上。在电脑上批准或回答后，那次工具调用执行完会触发 `PostToolUse`（执行失败为 `PostToolUseFailure`），据此收掉它的审批或提问按钮（2026-10-13 追加）。`PermissionRequest` 不带 tool_use_id，所以按"工具名 + 工具输入"对应是哪一次请求，并行的别的调用不会误收。这两个 hook 每次工具调用都触发，注册为 `async`，Claude Code 不等它（relay 启动一次约 0.4 秒）；relay 发送前去掉载荷里的工具结果，守护进程也不为它写日志。批准后工具运行很久的，按钮要等它跑完才收。在 Desktop 里点「拒绝」时没有任何 hook：Claude Code 直接中断回合（工具显示 Stopped），`Stop` 不在用户中断时触发，`PostToolUseFailure` 和 `PermissionDenied` 也都不管手动拒绝（官方 hooks 文档，2026-10-13 核对；同日 12:17 实测日志里 `PermissionRequest` 之后什么都没有）。但 Desktop 拒绝时会立刻在会话记录（transcript）里写一条被拒的工具结果，所以改看记录：该会话最近一次 hook 带来的记录路径记在内存里，按"工具名 + 工具输入"找到审批或提问对应的最后一次调用，已有结果就收掉它的按钮（2026-10-13 追加）。检查时机是该会话的下一次 `UserPromptSubmit`，外加每分钟一次扫描（拒绝后没再发指令也会收）。`UserPromptSubmit` 本身仍不直接收审批：回合中途发的消息也触发它，那时请求可能还在等；记录里那次调用还没有结果，就不收。只读记录末尾 1 MB，读不到、找不到这次调用都按"还在等"处理，不会误收。
- 排版：回答里的 Markdown 转成 Telegram 格式（粗体、代码、代码块、标题、列表、链接；表格按行转成「• 甲 · 乙 · 丙」）。第一行是状态和会话标题，第二行是用户最后一句；然后是正文、选项和官方建议，会话标记放在最后一行。Telegram 拒收格式时改用纯文本重发这一条。
  - 选项段上方的标签跟着回答的语言走：回答用 `Options:` 标题时显示「Options」，否则显示「选项」（2026-10-13 用户要求；之前一律显示「选项」，英文会话里是中文标签配英文选项）。
- "用户最后一句"只取用户真正输入的内容；会话里收到的系统消息（CI 事件、后台任务通知、其他会话发来的消息等）不算。
- 会话识别：会话标题加用户最后一句的前 30 字。标题优先取 Desktop 侧边栏标题，不用 `SessionStart` 的内部短名。
- 会话标记：每条通知第一行末尾带 `#` 加 `session_id` 前 8 位。
- 自由 prompt 路由：回复某条会话消息就发给那个会话；否则发给最近一次通知的会话。
- **话题模式**（2026-10-11 用户在 BotFather 打开 threaded mode 后追加）：守护进程启动时用 `getMe.has_topics_enabled` 判断。开启时每个会话一个话题，名字是「会话标题 #标记」，会话改名时话题跟着改名；该会话的所有通知都发进这个话题。
  - 在会话自己的话题里直接打字就发给那个会话，不用回复；回复某条通知仍然优先。
  - 机器人的回执（已发送、拒绝原因、/status）回到用户操作的那个话题；启动提示和故障提醒发在主对话里。
  - 会话和话题的对应关系存在 `%USERPROFILE%\.ccmonitor\topics.json`，只有 id 和话题最后活动的时间，没有标题和内容，避免重启后重复建话题。对应关系丢了时，从话题名里的标记找回。
  - **3 天没有动作的话题自动删除**（2026-10-12 用户要求）：发进话题的通知、用户在话题里回复或点按钮都算动作。守护进程启动 1 分钟后检查一次，之后每小时一次，用 `deleteForumTopic` 删除（连同其中的消息）；删除失败的下次再试。会话之后再有通知时新建话题。旧文件里没有时间的话题，从升级后第一次启动算起。
  - **在「All Messages」里发命令不留下新话题**（2026-10-13 用户要求）：Telegram 客户端在 All Messages 里发任何消息都会以它为名新建一个话题。命令落在不属于任何会话的话题里时，照常执行，回答改发主对话（不带话题），再删掉这个话题。名字里带会话标记的话题算会话的，不删。命令不一定落进那个新话题（2026-10-13 重启后出现两个空的「/away」话题），所以 Telegram 一报告新建了以「/」开头、不带会话标记、也不属于任何会话的话题，就立即删掉。
  - 话题被删掉后，下一条通知会重新建一个。用户自己建的话题没有对应会话，在里面打字会收到说明。
  - 消息和会话的对应关系只在内存里，守护进程重启就丢。这时从被回复消息文字里的会话标记找会话；找不到就拒绝，绝不转给别的会话。
  - 重启前发出的按钮失效，点了会提示改用回复。
- 点选项时写入的是该项的**完整文字**，不是编号。
- 常驻：开机自启；有 Telegram 命令可暂停/恢复。
- 失效时每天最多提醒一次，其余静默降级。

### 3.4 事件来源

- 主：官方 hook 事件，在模型之外运行，不进上下文。会话用 `session_id` 识别。
  - 立刻级：只用 `PermissionRequest`。`tool_name` 为 `AskUserQuestion` 时是 Claude 提问，其余是权限审批，`tool_input` 带命令全文。不依赖 `Notification(permission_prompt)` 和 `idle_prompt`。
  - 延后级：`Stop`，`last_assistant_message` 直接提供回答全文和选项段。
  - 写入「拒绝」后不会有 `Stop`，侧通道自己把这次审批标为结束。
- 兜底：会话记录文件（`transcript_path`），只在 `Stop` 缺失时用。
- 无障碍树不用于读事件，只用于写入。

### 3.5 写入

- 走无障碍操作：切到目标会话、填入文字、点发送；审批点"允许一次"或"拒绝"。
- 写入序列：恢复窗口（最小化时必须先恢复）→ 每次都先发一次距离为 0 的模拟鼠标移动点亮显示器（2026-10-12 改：原来只在渲染窗口不在时才发，但 21:31–21:57 熄屏期间渲染窗口一直在，没点亮，那段时间的切换全部失败）；电脑已静止 1 分钟以上时再等 1.5 秒让显示器亮起；渲染窗口仍不在就再发，最多 3 次 → 关掉遮挡的提示框 → 切到目标会话 → 填字 → 等 `Send` 可用且读回长度一致 → 点 `Send` → 以 `UserPromptSubmit` hook 或按钮变为 `Stop` 确认送达 → 切回原会话 → 恢复原窗口状态。
- 定位：输入框 `Edit`/`Prompt`，发送 `Button`/`Send`；审批按钮在当前会话的审批卡片内按前缀 `Allow once` / `Deny` 匹配。读按钮名时先转成字符串，因为界面里有 Name 为空的按钮。
- 切到目标会话最多等 15 秒，对话很长的会话打开较慢。
- **会话正在运行时，手机发来的 prompt 照发，作为插话送进这一轮**（2026-10-12 用户改定，原为拒绝并排队到这一轮结束）。实测（2026-10-12 19:41）：运行中 Desktop 显示 Stop、不显示 Send，输入框填字后 Send 出现，点下后消息在这一轮中途送达模型。此时 Stop 一直在，所以只以输入框清空确认已发出；Telegram 回「已发送：会话正在运行，作为插话送达这一轮」。模式 B 换班写入的 `/clear` 和启动指令不插话，仍在会话运行时拒绝。
- 以下情况拒绝写入，并在 Telegram 说明原因：
  - 审批时会话没有等待审批的请求，或卡片里的命令和通知里的不一致。
- 点了发送或审批按钮、却确认不了结果时，在 Telegram 报"可能未发送/可能未审批"，请用户到电脑上确认，不自动重试。
- 目标会话输入框里有草稿时，prompt 照发：先把草稿原文读到内存，填入 prompt 并发送，再把草稿填回输入框（2026-10-12 用户选定）。草稿没能填回时，在 Telegram 报告并附上草稿原文，不会丢。官方建议的读取和发送仍然在有草稿时拒绝。
- prompt 写入因界面写入故障而失败时，由守护进程自己排队重发，不需要 agent（见第 5 节）。"可能未发送"不重发，以免发两次。
- 只在**离开状态**允许：电脑连续 3 分钟无键鼠输入（2026-10-12 用户改定：原为 10 分钟，先改 1 分钟，因 40 分钟内来回切换 5 次又改为 3 分钟），或用户在 Telegram 声明离开，任一成立。
  - 代价：在电脑前看长回答、3 分钟没动键鼠，也算离开：通知会发到 Telegram，读官方建议会切换会话，模式 B 的换班也可能在这时写入。
  - 写入为点亮显示器发的模拟鼠标移动是 ccmonitor 自己的输入：脚本把"之前最后一次真实输入"和"这次模拟输入"的时间报给守护进程，判断离开时跳过它，所以不会让离开状态失效（2026-10-12 用户选定的做法）。
    - 脚本只在退出时才报这两个时间，中间最长 50 秒。2026-10-12 实测：这段时间里的离开判断把那次模拟鼠标当成了用户，刚发的 /away 几秒后就失效，通知因此不发。改为整段驱动运行都算 ccmonitor 自己的输入：开始运行前记下当时的真实输入时间，运行期间比它新的输入一律按自己的算，运行结束再把这一段并进上面的链里。代价是运行的那几十秒内用户真碰了键鼠也会被吸收，这和原来"结束前几秒的触碰也被吸收"是同一个取舍。
  - 声明有两种：发 /away；或在 Telegram 回复、点按钮（2026-10-11 用户确认，免去先发 /away）。原先回复要求电脑已有 1 分钟没有键鼠输入，2026-10-14 用户要求去掉：手机在手上就是不在电脑前，等一分钟没有意义。现在回复和按钮一样，总是写入并声明离开。
  - 声明在电脑下一次有键鼠输入时失效。
  - 例外：在 Telegram 点**任何按钮**（选项、官方建议、允许一次、拒绝、提问的选项）都总是执行，不看电脑是否有人在用，并同时声明离开，让这一轮回答照样带选项（2026-10-11 用户确认；审批按钮于 15:45 加入）。2026-10-14 起自由回复也一样。审批照样先核对命令和通知里的一致。
- 操作完切回离开时打开的那个会话，窗口恢复原状（原来最小化就再最小化）。
- 审批只给"允许一次"和"拒绝"两个按钮；消息带命令全文，超过 1000 字截断。"总是允许"留在电脑上做。

### 3.6 安全

- 只接受一个固定 Telegram chat id 的消息，其余丢弃。不做二次确认。
- 审批允许走 Telegram。**用户已知晓并接受**：会话跑在 bypass 模式，Telegram 账号的安全等级从此等于电脑的安全等级。
- 侧通道看到的任何会话内容和用户输入**一字不落盘**；日志只记事件名、时间和写入结果代码。
- 日志每天零点轮换为 `daemon.log.YYYY-MM-DD`，只留最近 3 天（2026-10-14 用户要求，暂定 3 天）。轮换时按个数删；守护进程启动时再删一遍修改时间超过 3 天的旧日志，补上关机那几天，也清掉原来按大小轮换留下的 `daemon.log.1`/`.2`。

### 3.7 红线

- 不污染会话上下文（每轮一行选项指令是唯一例外，见 3.2）。
- 用户在电脑前时，Desktop 的界面和操作流程不变；例外是回答末尾的选项段（3.2）。在电脑前不读官方建议（3.8），不会切换会话。
- 不替换、不包装 Desktop 自己管理的任何文件。
- 不再尝试给 Desktop 挂调试接口。

### 3.8 官方建议按钮（2026-10-11 追加，Q55–Q59）

- **读法**：切到目标会话，在输入框为空时用 PostMessage 向 Desktop 的渲染窗口发一次 Tab，灰色建议变成真实文字，用 ValuePattern 读出原文，再把输入框清空；灰色建议随即回来，用户回到电脑时看到的和原来一样。
  - 实测稳定（连续 3 次同一句；切走再切回仍在），所以 Telegram 上显示的就是**原文**，不用 OCR，也不截屏（Q55 的方案 b）。
  - PostMessage 不改变键鼠空闲时间，不会让离开状态失效；不用模拟键盘。
- **何时读**（Q56、Q57）：完成通知照旧立即发出。之后若处于离开状态，切到该会话、恢复并前置窗口，最多等约 30 秒等建议出现，没等到就过 1 分钟再读一次（长会话的建议可能 35 秒后才出现，2026-10-12 实测）；读到就编辑那条 Telegram 消息，加一行「💡 官方建议：<原文>」和一个「💡 官方建议」按钮。然后切回原会话、恢复原窗口状态，和写入的做法一致。
  - 2026-10-12 用户改定：**只在离开状态读**，在电脑前不读（取代 2026-10-11 19:08 的"在电脑前等键鼠静止 10 秒再读"）。1 分钟后的第二次读取前若已回到电脑前，也不读。
- **点按钮**（Q58）：目标会话正在运行或输入框不为空时拒绝。否则重新按 Tab、读出输入框原文、点发送，并把实际发出的原文回显到 Telegram。读不到建议（输入框仍为空）也拒绝。
  - 按钮带着通知上显示的原文。接受后的文字和它不一致（会话已经往下走、建议换了）就不发送，把通知更新为当前建议，让用户再点一次。这样发出的永远是用户看到的那句。
  - 点按钮和点选项一样，不受离开状态限制，并同时声明离开。
- **与选项并存**（Q59）：选项保留；建议是额外的一个按钮。读不到建议时选项照常可用。
- **失败**：建议读取或发送"坏了"（找不到窗口、切换失败等）走现有的故障提醒（每天最多一次）。没有建议是正常情况，不提醒。
- **时限**（2026-10-12 追加）：守护进程给驱动脚本的硬超时原为 60 秒，而读建议各步上限加起来约 87 秒；Desktop 忙时（20:03、20:05 实测）脚本被杀，收尾的切回原会话、恢复最小化都没执行。现在脚本自己守 50 秒总时限：切换会话最多用剩余时间（至少 5 秒），等建议只用剩下的时间，并为切回原会话留 12 秒；时间用完返回 `out_of_time`（算故障）。硬超时提到 90 秒，只作兜底。切换超时后点击仍可能迟到生效，切回前先等它落定。每次写入在日志里记下各步耗时（毫秒），不含内容。
- **约束**：建议原文只在内存里，日志只记结果代码；屏幕操作和写入在同一个工作线程里排队，不会互相抢窗口；多个会话同时完成时依次处理。

### 3.9 提问按钮（2026-10-11 追加）

- 起因：「🔴 Claude 提问」原来只把问题和选项列成文字。回复会被当成新 prompt，而会话正等着回答，界面写入返回"正在运行"，只能排队走辅助会话，等提问在别处答完才送到（2026-10-11 16:53–17:04 实测）。
- **按钮**：提问通知每个选项一个按钮，点了就用无障碍接口点 Desktop 提问卡片里对应的选项，和审批按钮的做法一样。
- **一次一个问题**：Desktop 的卡片一次只显示一个问题，答完自动跳到下一个。所以通知正文列出全部问题，按钮只给当前这一个；答完后同一条消息的按钮换成下一个问题的，全部答完按钮消失。按钮写成「问2·选项」以示是第几个问题。
- **多选**：每个选项一个勾选按钮（☐/☑），勾选只改 Telegram 上的按钮，不碰屏幕；点「提交所选」才去 Desktop 把勾选设成一样（没勾的包括 Other 都取消），再点 `Next` 或 `Submit`。一项都没勾就提交会被拒绝。
- **拒绝**：会话没有提问卡片；卡片当前的问题（文字和"第几个/共几个"）和按钮对应的不一致；Desktop 里找不到名字和通知一致的选项（按「标签 说明」比对，单选去掉末尾的快捷键数字）。被拒绝时按钮留着，可以再点。
- **确认**：点完后等卡片消失或换到下一个问题；没等到就再点，最多 3 次；还不行就报"可能未回答"，走故障提醒。
- 和其他按钮一样：不看离开状态，点了同时声明离开；屏幕操作在同一个工作线程里排队。
- 自由文字回复和「Other」不在这里处理：回复仍按 3.3 当作新 prompt。

- ~~辅助会话转发作为写入的备选路径~~ **已完成**（2026-10-11，PR #7）。
  - 只转发 prompt，不能审批。
  - 只在界面写入遇到会话正在运行、有草稿或界面写入坏了时才走这条路；已发出或"可能已发出"的不转发，以免发两次。
  - 实测：目标会话把转发来的消息当作"另一个会话的请求"照做，权限按它自己的设置；它不会因此改设置或批准待审批请求。
  - 搭建方法见 [helper-session.md](helper-session.md)。
- **守护进程内排队重发**（2026-10-12，取代辅助会话成为默认备选路径）。用户要求备选路径不靠 agent：辅助会话要常驻、每次转发和每 30 分钟重连都要一轮模型调用，且实测守护进程频繁断开它的连接。
  - 会话正在运行：prompt 留在守护进程内存里，收到该会话的 `Stop` / `StopFailure` hook 后约 3 秒用界面写入发出；另有每分钟一次的重试兜底（按 Esc 或拒绝结束的回合没有 `Stop`）。同一会话的多条按顺序发，一轮一条。

  - 重试时用户已回到电脑前：不写入，整个会话的排队消息作废，原文发回 Telegram，免得在有人用电脑时切换会话。

  - `/status` 显示排队条数、转发模式和转发会话状态。
- **转发模式 A / B**（2026-10-12，用户定）。
  - 模式 A（默认）：不借助 agent，即上面的守护进程内排队重发。
  - 模式 B：借助转发会话（最便宜的模型、effort low、Bypass permissions）；转发会话没连上或正在换班时按模式 A 排队。
  - 转发会话由用户手动新建（2026-10-14 改，原来由任一会话用 `start_session` 代建）：那个工具不是每个 Claude Desktop 版本都有，ccmonitor 要能给别人用。窗口的「新建转发会话」用官方深链接 `claude://code/new` 在存储目录的 `helper` 文件夹里打开一个填好启动指令的新会话，模型和 effort 由该文件夹的项目设置定（Haiku、low）；用户第一次信任文件夹、选 Bypass，再按发送（深链接有意只填不发，ccmonitor 不代按）。「复制启动指令」留作打不开链接时的后备；启动指令里的 Python 用运行 ccmonitor 的那个（不靠 PATH 上的 `python`），缺必需工具时转发会话自己说明并停下。
  - 切换：守护进程启动参数 `--relay-mode a|b`、Telegram `/mode a|b`、或会话里运行 `python -m ccmonitor.relaymode a|b|status`；选择存进 `%USERPROFILE%\.ccmonitor\relay-mode.json`。切到 B 而没有转发会话时，命令打印新建参数，由运行它的会话新建。
  - 模式 B 每 6 小时换班：转发会话不能在自动触发的回合里新建会话；自己清空会停掉转发源且没人唤醒（2026-10-12 实测）；删除会话每次都要用户在电脑上确认。所以由守护进程在离开状态下用界面写入 `/clear` 再写入启动指令（实测 `/clear` 后模型、effort、权限模式保留）。换班和转发同一个工作线程排队，正在进行的转发先完成。细节见 [helper-session.md](helper-session.md)。
